# 第 4 周 · Hive 查询优化记录

> 团队：云仓五号　日期：2026-11-19
> 环境：Hive 4.0.0（Tez 0.10.3） / ORC 存储 / Docker 单机

---

## 一、优化前的问题

第 3 周做 KPI 与 EDA 时遇到两类性能问题：

1. **全表扫描**：按月份过滤时写成 `substr(order_timestamp,1,7) = '2024-06'`，分区字段被函数包裹，Hive 无法裁剪分区，每次都扫 12 个月；
2. **明细表无裁剪**：品类分析直接对 `fact_order_item` 全表聚合，37,549 行全部参与计算。

数据量不大时感受不明显，但这是**写法问题**：数据量涨 100 倍后，全表扫描会直接超时。

---

## 二、优化措施与验证

### 2.1 分区裁剪（最有效）

| 写法 | 执行计划扫描行数 | 说明 |
|---|---|---|
| `where order_month = '2024-06'` | **1,154 行** | 分区字段直接过滤，只扫 1/12 分区 |
| `where substr(order_timestamp,1,7) = '2024-06'` | **15,000 行** | 函数包裹分区字段，退化全表扫描 |

验证方式（`explain` 输出中的 `TableScan` 行数）：

```sql
explain select round(sum(pay_amount),2) from ydsh_dwd.fact_order
where amount_invalid = 0 and order_month = '2024-06';
-- TableScan [TS_0] (rows=1154 width=111)

explain select round(sum(pay_amount),2) from ydsh_dwd.fact_order
where amount_invalid = 0 and substr(order_timestamp,1,7) = '2024-06';
-- TableScan [TS_0] (rows=15000 width=214)
```

**结论：扫描行数从 15,000 降到 1,154，减少 92.3%。**

### 2.2 存储格式：ORC

所有 DWD 表统一 `stored as orc`：

| 优点 | 说明 |
|---|---|
| 列式存储 | 只读查询涉及的列，`sum(pay_amount)` 不读其他字段 |
| 压缩 | 默认 zlib 压缩，磁盘占用约为文本 1/3 |
| 谓词下推 | `amount_invalid = 0` 在存储层过滤，减少传输 |

### 2.3 分桶（明细表）

`fact_order_item` 按 `order_id` 分 8 桶（`clustered by (order_id) into 8 buckets`）：

```sql
-- 按订单号查明细，只命中 1 个桶
select count(*) from ydsh_dwd.fact_order_item where order_id = 'O2024002724';
```

适用场景：**按订单号回查明细**（订单详情页）。不适合按品类聚合（仍需全桶扫描）。

### 2.4 Map Join 小表广播

维表（dim_user 1,000 行、dim_product 600 行）远小于事实表，Hive 自动选择 Map Join：

```sql
select count(distinct f.order_id)
from ydsh_dwd.fact_order f
join ydsh_dwd.dim_user u on f.user_id = u.user_id
where f.amount_invalid = 0 and u.province = '广东省';
-- Time taken: 1.19 秒（首次），后续 0.5 秒左右
```

必要时可显式加 hint：`/*+ MAPJOIN(u) */`。

### 2.5 提前汇总（DWS 层）

最根本的优化不是调查询，而是**不查明细**：

| 查询 | 数据源 | 行数 | 典型耗时 |
|---|---|---|---|
| 月度 GMV | `fact_order`（事实表） | 15,000 | 0.5~1.2 秒 |
| 月度 GMV | `dws_sales_month`（汇总表） | 12 | < 0.3 秒 |

因此 ADS/DWS 层已把常用指标预先算好，BI 与分析查询直接读汇总表。

## 三、优化前后对比

| 场景 | 优化前 | 优化后 | 提升 |
|---|---|---|---|
| 单月 GMV（分区字段被函数包裹） | 全表 15,000 行 | 单分区 1,154 行 | 扫描量 ↓92.3% |
| 月度趋势（ADS 层） | 扫事实表 15,000 行 | 扫 `ads_sales_daily` 366 行 | 扫描量 ↓97.6% |
| 品类分析 | 明细全表聚合 | `dws_category_month` 96 行 | 扫描量 ↓99.7% |
| BI 看板查询 | 直连 Hive（需 sasl 驱动） | MySQL 集市（2,320 行） | 毫秒级响应 |

---

## 四、规范（写进开发约定）

1. **分区过滤必须直接写在分区字段上**，禁止 `substr()/date_format()` 包裹；
2. 事实表查询必须带 `amount_invalid = 0`，同时限定时间范围；
3. 月度/品类/门店类指标优先读 `ydsh_dws` 与 `ydsh_ads`，不要回查明细；
4. 需要按订单回查明细时用 `fact_order_item`（分桶键是 `order_id`）；
5. 新增 ETL 脚本统一使用 ORC 存储。

---

## 五、局限说明

- 本机为单节点 Docker，数据量 15,000 行，绝对耗时差异只有几百毫秒，**优化效果主要体现在「扫描行数」而非「墙上时间」**；
- 真实集群上分区裁剪的收益会随数据量线性放大；
- 未做数据倾斜处理（当前数据分布均匀，`user_id` 最大分组 27 单，不存在热点 key）。若真实业务出现大 key，需要加盐打散。
