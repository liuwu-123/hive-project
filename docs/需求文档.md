## 一、项目背景

「云购生活」是一家虚构的新零售企业，业务同时覆盖线下门店与线上渠道（APP / 小程序 / PC 官网）。企业当前面临三个问题：

1. **数据分散**：用户、商品、门店、订单、明细、行为六类数据以 CSV 形式各自导出，没有统一口径；
2. **数据质量差**：枚举取值混乱（性别 8 种写法、会员等级 12 种写法）、金额存在负值与极端值、日期有 3 种格式、订单存在重复；
3. **无法支撑决策**：管理层只能看到零散报表，无法回答"这个月卖得怎么样""哪个品类在赚钱""会员体系有没有用"这类问题。

因此需要建设一套**企业级数据仓库 + 经营分析可视化系统**，把原始数据变成可复用、可追溯、可展示的指标资产。

## 五、指标体系定义

所有指标必须满足：**唯一口径、可从明细复算、有明确过滤条件**。

| 指标 | 口径 | 数据源 | 过滤条件 |
|---|---|---|---|
| GMV | `SUM(pay_amount)` | `fact_order` | `amount_invalid = 0` |
| 订单量 | `COUNT(DISTINCT order_id)` | `fact_order` | `amount_invalid = 0` |
| 客单价 AOV | GMV ÷ 订单量 | 同上 | 同上 |
| 活跃用户数 | `COUNT(DISTINCT user_id)` | `fact_order` | `amount_invalid = 0` |
| 复购用户数 | 下单 ≥2 次的用户数 | `fact_order` | `amount_invalid = 0` |
| 复购率 | 复购用户数 ÷ 下单用户数 | 同上 | 同上 |
| 品类销售额 | `SUM(item_amount)` | `fact_order_item` | `qty_invalid = 0` |
| 品类销量 | `SUM(quantity)` | `fact_order_item` | `qty_invalid = 0` |
| 用户累计消费 | 按 `user_id` 汇总 `pay_amount` | `fact_order` | `amount_invalid = 0` |

**两条铁律**：

1. 「有效订单」的唯一定义是 `amount_invalid = 0`，任何金额类指标必须带上；
2. **品类销售额（明细口径）与 GMV（实付口径）不可相加、不可互相校验**——本项目实测两者相差约 14.21 倍，报告中必须分别标注。

## 九、范围边界（本项目不做的事）

明确边界，避免验收时被误解：

1. **不做实时流处理**：数据为离线批处理，无 Kafka/Flink；
2. **不做数据写入回业务系统**：本系统只读，不承担业务库职责；
3. **不做用户权限体系**：Superset 仅使用单管理员账号，RBAC 未启用；
4. **不做多租户**：单团队单环境；
5. **预测模型不做长期外推**：仅预测 7 天，且报告中说明数据局限。
